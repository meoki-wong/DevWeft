# DevWeft 技术实施方案

> 本文是实施顺序、验收规则与模型协作约定的单一入口。每个工作包必须按「目标 → 代码 → 自动化验证 → 记录 → 下一包」完成。实施状态同步到 `docs/implementation-records/`。

## 1. 项目目标与边界

将 DevWeft 整理并演进为任何团队都能本地启动、接入自己的 Git 仓库、配置测试套件并查看可信运行证据的开源工程平台。MCP 工具继续作为主要交互方式；本计划围绕可安装、可配置、可解释、可验证、可扩展来补足产品闭环。

本轮约束：

- 不增加 Jenkins、CI 流水线或 MR 预审；自动化发布验证由本地命令执行。
- 暂不扩展 token 鉴权方案；保留现有认证实现和安全边界，不以此作为本计划前置条件。
- 保留 Windows 入口 `deploy.cmd`、`start.cmd`、`start-primary.cmd`、`start-standby.cmd`，并确保部署文档与 Linux/macOS 路径可用。
- PostgreSQL、虚拟机、Hyper-V 和主备能力必须有明确的安装/预检/故障提示；开发者无这些能力时仍可通过 SQLite 示例完成基础体验。
- 不把真实密钥、公司品牌/内网域名、私有镜像、VHDX、数据库或私有业务样例提交到仓库。
- 使用可复现、最小化、跨平台的公开示例；适配器默认不连接任何供应商。

## 2. 成熟产品可借鉴的正反馈能力

参考成熟测试平台、代码托管平台和可观测产品的共性，按优先级形成：

1. **接入引导**：检查环境、识别仓库、提供 dry-run、一次性生成项目配置和示例套件。
2. **可信运行结果**：保留测试计划、用例集合、配置版本、运行日志、失败分类和制品引用；结果可复查、可下载。
3. **失败反馈闭环**：把失败转换成可操作原因、修复建议、重试条件和相似历史经验；修复后可以对照前后结果。
4. **趋势和比较**：支持运行对比、失败率/耗时/覆盖趋势，并说明数据口径与证据来源。
5. **低风险扩展**：Git 提供方、测试模板、执行后端、制品存储通过小接口接入；默认实现本地可跑。
6. **开源贡献体验**：清楚的安装矩阵、配置 schema、故障排查、开发者指南、可离线验证的发布检查。

不为了“对标”而增加复杂审批、强制云账号或隐式上传数据。所有反馈必须来自真实运行证据，不能把跳过、豁免、未执行标记成通过。

## 4. 每个工作包的实现规则

1. 先确认仓库当前实现与已有测试，避免重造能力；对确实过时的断言说明依据后修订。
2. 新的命令、配置、数据库字段必须有输入校验、错误码/错误消息和向后兼容说明。
3. 迁移遵循 append-only：已发布迁移文件不改；变更写新版本迁移。开发阶段若必须修正尚未发布的历史迁移，要记录影响、备份策略、受影响版本和显式恢复指令。
4. 不吞启动/迁移/备份/恢复异常；只允许对明确可选依赖降级，并把降级状态暴露给用户。
5. 默认安全：参数数组优先于 shell 字符串、配置原子写、路径限定在工作区、制品和诊断包脱敏。
6. 不把环境不可用写成测试通过。真实 PostgreSQL、Hyper-V 和主备验收需单独注明真实环境与时间。
7. 每个工作包结束更新 `docs/implementation-records/<ID>.md`：改动、设计决定、测试命令与结果、未验证环境和风险。
8. 每次变更保持可回滚；无明确要求不推送、不合并、不发布。

## 5. 验收门槛

### 通用门槛

- `npm test` 全部通过；跳过项有原因，失败不能通过降低断言强行消除。
- 所有新增文档中的命令可在公开仓库根目录复现。
- `git diff --check` 通过；公共残留扫描无实际内部品牌、域名、密钥、Jenkins/MR 预审流水线配置。
- Windows CMD/PowerShell 文件做静态检查；需要 Windows/Hyper-V 的结论只由真实 Windows 环境给出。

### 数据门槛

- 空 SQLite、代表性旧 SQLite 和连续重复迁移无结构漂移/数据丢失。
- 迁移版本/名称/checksum 不匹配时启动失败，原账本值保持不变。
- PostgreSQL 迁移/基线可在真实 PostgreSQL 或 PGlite 契约测试下验证；真实 PG 部署能力单列验收。
- 备份缺失、哈希不符、DB 类型/版本不匹配时 restore 失败并保留原库。

### 产品门槛

- 新项目不依赖私人服务即可完成接入、运行样例和获取解释/诊断。
- 每一条指标能追溯到运行证据与统计分母；未知值不得被渲染成成功。
- 插件替换默认实现时通过同一契约测试。
