# D04 — 主备与制品故障级别

## 交付

- PM2 只在 `AWP_DB_DIALECT=postgres` 时启动独立 `awp-blob-store`；SQLite 继续通过控制面使用本地 blob 目录。主机控制面与 blob 服务共享 `AWP_BLOB_ROOT`，避免健康检查和上传实际落到不同目录。
- `/api/health/ready` 返回节点角色、执行模式、blob 模式/状态、缓存与持久性边界和恢复动作。主机本地 blob 不可用时 readiness 为 503；备用机远端 blob 不可达时 readiness 为 503；主机独立 standby 上传端点降级单独报告，不会掩盖主机本地服务仍可用的事实。
- 独立 blob 服务增加 readiness，验证 PostgreSQL 查询及本地存储读写状态。
- Standby 不创建本地 blob 目录、不提供会把工件错误写入备用机磁盘的 blob 上传路由；standby blob route 返回稳定的 `BLOB_STORE_UNAVAILABLE` 503。远端断连、超时、限流和服务端错误在客户端映射为同一可恢复错误；快照哈希错误保留原错误码与明细。
- 主机/备用机启动脚本等待角色化 readiness；Windows 部署验收验证主角色、本地存储和 PostgreSQL 模式下的独立上传端点状态。
- 新增 `docs/AVAILABILITY.md`，说明控制面主备与制品高可用差别、readiness 字段、故障影响、恢复步骤和备份边界；ONBOARDING 与部署配置样例已链接该说明。

## 设计决定

- 共享 PostgreSQL 不等于 blob 复制。主机本地 `data/blobs` 是规范副本；备用机没有本地缓存或持久化重试队列。远端恢复后重试提交，不能把数据库状态误报为制品已复制。
- 备用机 readiness 检查其配置的主机 blob endpoint；主机 readiness 检查自身本地存储。PostgreSQL 主机还单独监测 standalone blob endpoint，因为它服务备用机，但其故障不应误报主机本地控制面不可用。
- `BLOB_STORE_UNAVAILABLE` 是稳定的 503 错误码；不会把 endpoint、token、路径或底层连接异常写入错误响应。

## 验证

- 定向：`npx vitest run test/blob-health.test.mjs test/platform-settings.test.mjs test/remote-blob-store.test.mjs test/network-deploy-safety.test.mjs test/contracts.test.mjs test/postgres-baseline.test.mjs` — 6 个测试文件、53 项通过。
- 全量：`npm run verify:release` — 139 个测试文件，1146 项通过、6 项因环境前置条件跳过；残留扫描、OpenAPI/配置/lockfile、依赖树及完整 Vitest 套件均通过。可选联网 audit 未执行。
- `node --check` 覆盖 health、blob health/client/routes、blob server、server entry 和 PM2 配置，通过。

## 未实机验证与后续

- 当前执行环境为 macOS，没有 Windows PowerShell/CMD、PM2 Windows、真实 PostgreSQL 服务或 Hyper-V。Windows 启动流程、PM2 进程实际角色、真实 PG 的磁盘与 failover 行为仍需 D05 手工矩阵验证。PGlite PostgreSQL 基线契约测试通过，但不替代真实 PostgreSQL。
- blob readiness 只验证目录可读写和远端 readiness，不证明备份可恢复或跨主机复制已完成；恢复必须按备份文档实测。
