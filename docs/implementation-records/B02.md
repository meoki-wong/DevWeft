# B02 — 数据迁移、校验和、就绪检查

## 交付

- 增加 SQLite/PG 迁移清单，含版本、名称、校验和；checksum/name 不一致时启动迁移直接失败，保留原账本。
- v27+ SQLite 迁移与账本登记保持同一事务；单步迁移错误不再吞掉并继续启动。
- PG patchup 的 DDL 与账本登记改为同一事务，已存在的版本遇到 checksum 漂移会拒绝改写；PG 分支返回并等待迁移 Promise。
- v8 对旧协作层 `experiences(repo, ...)` 与新 testing schema 的差异做显式兼容：只跳过不适用于旧表结构的 `repo_id` 索引，其余 v8 DDL 原子执行；旧 `test_failures` 列按实际结构避免重复 ALTER。
- v28 水位回填明确识别 `experiences.id` 和 `experiences.experience_id`，只有表不存在时才不回填；缺少支持的 ID 列会报错。
- 删除迁移 SQL 文件缺失时降级跳过的行为；关键兼容列补齐错误会阻断启动。
- readiness 现在验证真实数据库方言、关键表/列/索引、每个已发布迁移的 ledger 记录与 checksum，并返回真实最高迁移版本。

## 验证

- 定向迁移/readiness/PG 测试：`npx vitest run test/v27-experiences-convergence.test.mjs test/platform-settings.test.mjs test/postgres-baseline.test.mjs --reporter=dot`，21 项通过。
- 全量测试：`npm test -- --reporter=dot`，131 个文件通过，1109 项通过、6 项跳过。
- PG patchup 在 PGlite 上基于公开 PostgreSQL baseline 测试了首次运行、重复运行、checksum 漂移、ready 200 与损坏账本时 ready 503。

## 限制与后续

- 本轮 PostgreSQL 覆盖通过 PGlite 与项目 baseline；尚未连接独立运行的 PostgreSQL 服务做真实部署矩阵。
- readiness 刻意只依赖控制面关键表与索引，不把可选 worker、VM、远程 blob 后端作为数据库 ready 的硬依赖。
- migration 文件按 append-only 管理；未来 schema 变化必须新增迁移版本。
