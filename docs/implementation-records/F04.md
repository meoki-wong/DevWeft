# F04 — Failure diagnostics workbench

## Delivered

- Added `GET /api/testing/runs/{runId}/diagnostics` with run-level phase, failure analysis, execution timeline, matching same-repository failures, reviewed experiences, and one evidence-linked next-step suggestion.
- Similar failures are scoped to the same repository, case key, and classified failure class. Similar experiences are returned only when linked to a matching failure or tagged for the matching class/case.
- Added confirm/ignore feedback through `POST /api/testing/runs/{runId}/diagnostics/{suggestionId}/feedback`. Feedback writes an append-only `testing_diagnostic_feedback` audit event. The latest event drives the displayed state; prior decisions remain in the audit history.
- Added a Failure diagnostics tab in the run evidence dialog. It renders source-backed suggestions and matching history; errors remain visible as unrecorded feedback.
- Added [FAILURE-DIAGNOSTICS.md](../FAILURE-DIAGNOSTICS.md) with endpoint, evidence, review and privacy contracts.

## Design decisions

- Suggestions derive from stored run reports and the existing deterministic failure classifier. No generated text is stored as a fact or automatically promoted into the experience library.
- Feedback confirms or ignores a proposed action only. It does not alter the run, test suite, or curated experience records.
- History matching stays within the run's repository to avoid cross-tenant information leakage.

## Verification

- `npx vitest run test/dashboard-testing-read.test.mjs test/cloud-testing-evidence.test.mjs --reporter=dot` — 2 files, 61 tests passed.
- The route test covers same-repository filtering, experience matching, confirm/ignore audit state, unknown suggestion rejection, and missing run handling. The UI test covers run ownership, evidence display, and refresh after the feedback response.
- `node --check testing/diagnostics.js` and `git diff --check` passed.

## Limits

- Dashboard API authentication continues to follow the project's existing deployment boundary; this work does not expand token authentication.
- Matching is deliberately exact on case key and failure class. It does not infer semantic similarity across differently named cases.
- Verification used SQLite fixtures and the local browser DOM harness; no production dashboard or PostgreSQL instance was exercised.
